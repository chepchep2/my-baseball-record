# Mobile Web Docs Redesign Design

## Goal

`마이베이스볼레코드`의 기획, 설계, 구현 계획 문서를
PRD 기준에 맞게 다시 정렬한다.

이 문서의 목적은 기존 문서의 충돌을 정리하고,
어떤 문서를 어떤 역할로 재작성할지 정리하는 것이다.
즉 이 문서는 제품 범위를 새로 정의하는 문서가 아니라,
문서 개편 작업을 안내하는 메타 문서다.

## Why This Redesign Is Needed

기존 문서 세트에는 아래 문제가 섞여 있다.

- 제품 핵심 가치는 `기록 확인`인데, 일부 문서는 입력 흐름 또는 구현 세부 사항에 무게가 쏠려 있다.
- 모바일 웹이 실제 목표 플랫폼인데, 와이어프레임과 일부 화면 기획은 데스크톱 기준으로 작성되어 있다.
- `README`, `docs/README`, `mvp`, `prd`, `design`, `frontend/backend plan` 사이에 저장소 구조와 v1 범위 설명이 어긋난다.
- 구현 계획 문서가 상세한 편이긴 하지만, 상위 제품 정의와 모바일 웹 제약을 직접적으로 다시 받쳐주는 구조는 아니다.

이 상태로 구현을 진행하면 프론트엔드, 백엔드, 화면 설계가 각자 다른 기준을 따라갈 가능성이 높다.

## Product Definition

### Product Type

v1은 `개인 선수 전용 모바일 웹 기록 관리 서비스`다.

이 서비스는 팀 운영 도구나 리그 운영 도구가 아니다.
또한 경기 입력 자체를 목적으로 하는 입력 전용 앱도 아니다.

### Non-negotiable Product Rules

아래 규칙은 v1에서 바뀌지 않는 기준으로 둔다.

- 계정 1개는 선수 프로필 1개와 연결된다.
- 사용자는 자신의 기록만 관리한다.
- 사용자가 다른 선수 기록을 대신 관리하는 모델은 v1에 넣지 않는다.
- 팀, 매니저, 기록원, 리그 운영자 관점 흐름은 v1 문서에 포함하지 않는다.
- 모든 대표 시나리오와 화면 흐름은 `개인 선수 본인` 시점에서 작성한다.

### Primary Problem

사회인 야구 개인 선수는 여러 출처에 흩어진 경기 기록을 한곳에 모아 시즌 성적을 쉽게 확인하기 어렵다.

### Core Value

사용자는 이 서비스에서 `내 야구 기록을 계속 모으고 관리할 수 있다`는 감각을 가장 강하게 느껴야 한다.

### Product Priority

제품의 중심은 `기록 확인`이다.
다만 `기록 입력`은 부차적 기능이 아니라, 기록 관리 가치를 유지시키는 핵심 행동이다.

즉 v1의 우선순위는 아래와 같다.

1. 기록이 한곳에 모이고 누적 관리된다는 감각
2. 이번 시즌 성적을 명확하게 확인하는 경험
3. 경기 후 기록을 실제로 계속 추가할 수 있는 입력 흐름

### Usage Context

모바일 웹 사용 맥락은 둘 다 고려한다.

- 경기 직후 현장에서 바로 기록 입력
- 나중에 집이나 이동 중에 기록 정리

하지만 제품의 기본 진입 경험은 `기록 확인 화면`이어야 하며,
재방문을 가장 강하게 만드는 행동은 `새 경기 후 기록 추가`로 본다.

사용자가 계속 써야겠다고 느끼는 순간은 `몇 경기 이상 기록이 쌓인 뒤 시즌 성적이 정리되어 보일 때`에 가깝다.

기록이 하나도 없는 경우에도 기본 홈은 온보딩 전용 화면이 아니라 `빈 기록 화면`으로 둔다.
즉 0 지표를 포함한 기본 기록 화면 구조를 먼저 보여주고, 그 안에서 `경기 추가`를 유도한다.

### Decision Rule

제품 판단이 갈릴 때는 `입력 속도`보다 `기록 관리의 명확성`을 우선한다.

## Mobile Web Principles

### Platform Principle

v1은 단순 반응형 웹이 아니라 `모바일 웹 우선` 제품이다.

문서와 설계는 아래 전제를 기본으로 가져간다.

- 작은 화면에서 처음부터 끝까지 사용 가능해야 한다.
- 한 손 사용과 짧은 집중 시간에 대응해야 한다.
- 네트워크가 불안정하거나 입력이 중단될 수 있는 상황을 고려해야 한다.
- 긴 입력 폼은 필드 축소가 아니라 단계 설계와 상태 설계로 부담을 낮춰야 한다.

### Mobile-web-first Constraints

모든 문서는 아래 기본 제약을 전제로 작성한다.

- 기본 설계 타깃은 일반적인 스마트폰 세로 화면이다.
- 데스크톱은 모바일 구조를 확장해 보여줄 수는 있지만, 새로운 핵심 정보 구조나 핵심 액션 배치를 따로 정의하지 않는다.
- 모바일에서 핵심 액션은 헤더 과밀보다 안정적인 접근성을 우선한다.
- 모바일 사용 중 입력이 끊길 수 있으므로, 비정상 상태와 이탈 흐름을 반드시 문서에 적는다.

### Information Hierarchy

기록 확인 화면의 첫 우선순위는 `이번 시즌 핵심 지표 요약`이다.
그다음 우선순위는 `경기 추가` 같은 입력 유도 행동이다.

즉 첫 화면은 조회 중심이지만, 사용자가 다음 행동으로 입력을 선택하기 어렵지 않아야 한다.

### Input Principle

v1에서는 기록 입력 항목 자체를 과도하게 줄이지 않는다.

사용자는 기본 기록을 모두 입력할 수 있어야 하며, 모바일에서의 사용성은 아래 방식으로 해결한다.

- 단계 분리
- 탭 상태 유지
- 숫자 입력 방식 최적화
- 저장/취소/이탈 상태 명시
- 오류 요약과 필드 오류의 병행 노출

여기서 `기본 기록`은 기존 화면 기획 문서에 정의된 타자 기본 항목과 투수 기본 항목 전체를 의미한다.
즉 모바일이라는 이유로 기본 항목을 삭제하거나 핵심 입력 범위를 축소하지 않는다.

### State Principle

모바일 웹 문서는 정상 흐름만 적지 않는다.
반드시 아래 상태를 포함해야 한다.

- 빈 상태
- 저장 중 상태
- 저장 실패 및 재시도 상태
- 이탈 시 확인 상태
- 인증 만료 상태
- 입력 중단 후 복귀 상태

입력 중단 후 복귀 상태의 v1 기준은 아래와 같다.

- 같은 세션 안에서 단계 전환과 탭 전환 시 입력값은 유지된다.
- 화면 이탈 시 경고를 제공한다.
- 완전한 로컬 드래프트 복구는 v1 필수 범위로 두지 않는다.

## V1 Scope

### Included In V1

- 구글 로그인 기반 인증
- access token / refresh token 기반 로그인 세션
- 경기 생성
- 타자 기록 입력
- 투수 기록 입력
- 시즌 기준 누적 기록 조회
- 통산 기준 누적 기록 조회
- 경기 유형 기준 필터 조회
- 개인 선수 소유 데이터 관리
- 빈 기록 화면을 기본 홈으로 제공

### Excluded From V1

- 이메일/비밀번호 인증
- 팀 생성
- 선수 등록을 통한 팀 로스터 운영
- 다중 선수 프로필 관리
- 타인 기록 대리 관리
- 팀 관리자/기록 담당자 기능
- 리그 운영 기능
- 외부 기록 자동 연동
- 최근 경기 전용 화면
- 타석별 상세 로그
- 이닝별 상세 로그
- 구글 외 소셜 로그인

## Documentation Architecture

문서 체계는 `개요 문서 1개 + 상세 문서들` 구조로 다시 정리한다.

### Authority Order

문서 간 충돌이 생기면 아래 순서로 우선한다.

1. `docs/prd.md`
2. `scenario` 문서
3. `design` 문서
4. 전체 구현 개요 문서
5. 프론트엔드/백엔드 상세 구현 계획 문서

즉 하위 문서는 상위 문서와 충돌하는 범위나 정의를 새로 만들 수 없다.

### 1. Repository README

`README.md`는 저장소 소개 문서다.
이 문서는 아래만 담당한다.

- 저장소 구조
- 현재 포함된 디렉터리
- 문서 허브 위치 안내

루트 README는 더 이상 상세 기획 문서 허브 역할을 하지 않는다.

### 2. Documentation Hub

`docs/README.md`는 문서 허브다.
이 문서는 아래를 담당한다.

- 현재 v1 제품 방향 요약
- 읽는 순서
- 각 문서의 역할 설명
- 최신 기준 문서 안내

### 3. Product Scope Source

`docs/prd.md`를 단일 범위 기준 문서로 사용한다.

이 문서는 아래를 소유한다.

- 문제 정의
- 대상 사용자
- 핵심 가치
- 대표 시나리오 요약
- 포함 범위
- 제외 범위
- 모바일 웹 제약
- 성공 기준

`docs/mvp.md`는 문서 충돌을 줄이기 위해 제거하고, 내용을 `docs/prd.md`로 흡수한다.

### 4. Scenario Document

`docs/superpowers/specs/2026-03-17-scenario-v1.md`는 대표 사용 흐름을 담당한다.

이 문서는 아래를 분명히 해야 한다.

- 기록 확인이 기본 진입이라는 점
- 경기 후 기록 추가가 재방문 트리거라는 점
- 누적된 시즌 성적 확인이 장기 가치라는 점

### 5. Mobile Product Design Documents

설계 문서군은 모바일 웹 기준으로 다시 정리한다.

핵심 역할은 아래와 같다.

- 모바일 웹 정보구조
- 화면별 목적
- 화면별 상태
- 입력/조회 우선순위
- 검증 규칙
- 비정상 상태 처리

기존 `baseball-record-v1-design`, `screen-planning-v1`, `frontend-ascii-wireframes`는
이 기준에 따라 재작성하거나 역할을 재정의한다.

### 6. Overview Implementation Plan

상세 구현 계획 전에 `프론트엔드 + 백엔드 전체 개요 계획 문서`를 먼저 둔다.

이 문서는 아래를 담당한다.

- 제품 구현 범위 요약
- 프론트엔드 책임
- 백엔드 책임
- 공통 계약 지점
- 구현 순서

이 문서는 제품 범위를 다시 정의하지 않고, 상위 문서를 어떤 구현 단위로 나누는지만 설명한다.

### 7. Detailed Frontend And Backend Plans

프론트엔드와 백엔드 구현 계획은 별도 문서로 분리한다.

두 문서는 모두 아래 원칙을 따른다.

- 상위 제품 문서의 범위만 구현한다.
- 새 범위를 추가하지 않는다.
- 모바일 웹 제품 정의와 API 계약을 직접 참조한다.
- `writing-plans` 기준으로 단계, 파일, 테스트, 검증 명령을 상세히 작성한다.

### Rewrite Output Contract

각 재작성 문서는 아래 질문에 답할 수 있어야 한다.

- 이 문서의 책임은 무엇인가
- 이 문서가 결정하는 것은 무엇인가
- 이 문서가 결정하지 않는 것은 무엇인가
- 바로 아래 단계 문서가 무엇을 이어받아야 하는가

1. `docs/prd.md`
2. `docs/README.md`
3. `README.md`
4. `docs/superpowers/specs/2026-03-17-scenario-v1.md`
5. `docs/superpowers/specs/2026-03-16-baseball-record-v1-design.md`
6. `docs/superpowers/specs/2026-03-17-screen-planning-v1.md`
7. `docs/superpowers/specs/2026-03-17-frontend-ascii-wireframes.md`

### Documents To Remove Or Merge

- `docs/mvp.md`
  - `docs/prd.md`로 흡수 후 제거

### Documents To Create

- 프론트엔드와 백엔드를 함께 설명하는 상위 구현 개요 문서 1개
- 필요 시 API 계약 문서 1개
- 이후 `writing-plans` 기반 상세 프론트엔드 계획 문서
- 이후 `writing-plans` 기반 상세 백엔드 계획 문서

## Frontend Design Direction

프론트엔드 문서는 아래 전제를 따라야 한다.

- 첫 진입은 기록 확인 화면
- 데이터가 없어도 기록 확인 화면이 홈
- 첫 화면의 우선순위는 이번 시즌 핵심 지표 요약
- 두 번째 우선순위는 경기 추가 행동
- 기록 입력은 단계형 구조로 설계
- 전역 탭바보다 기록 화면 중심 단일 흐름을 우선
- 모바일에서 상단 액션 과밀을 피함
- 입력 중단, 저장 실패, 인증 만료 같은 상태를 문서에 명시

## Backend Design Direction

백엔드 문서는 아래 전제를 따라야 한다.

- 개인 선수 소유 데이터 모델을 유지
- 인증, 경기 입력, 누적 기록 조회를 v1 핵심 API로 본다
- 최근 경기 전용 기능은 v1에서 제외한다
- 프론트가 필요로 하는 통합 기록 요약/상세 지표 구조를 명시적으로 지원한다
- refresh token 기반 인증 흐름을 명확히 문서화한다

## Review Criteria

문서 전면 개편 후 아래 질문에 모두 `예`라고 답할 수 있어야 한다.

1. 이 제품이 개인 선수용 기록 관리 서비스인지 분명한가
2. 모바일 웹 기준 제약이 모든 상위 문서에 반영되었는가
3. PRD가 단일 범위 기준 문서 역할을 하는가
4. 설계 문서가 조회 우선 제품 구조를 일관되게 설명하는가
5. 프론트엔드와 백엔드 계획 문서가 상위 범위를 벗어나지 않는가
6. 구현을 시작하는 사람이 읽는 순서를 헷갈리지 않는가

## Next Step

이 설계 문서를 기준으로 실제 문서를 다시 쓰고,
그 후 `writing-plans`를 사용해 아래 순서로 구현 계획을 재작성한다.

1. 전체 구현 개요 문서
2. 프론트엔드 상세 구현 계획
3. 백엔드 상세 구현 계획
