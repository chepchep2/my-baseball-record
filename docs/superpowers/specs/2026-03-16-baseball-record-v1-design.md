# Baseball Record V1 Design

## Goal

개인 선수 전용 모바일 웹 기록 관리 서비스로서의 Baseball Record v1을 설계한다.

이 문서는 PRD가 고정한 제품 범위를 바탕으로,
v1이 어떤 정보구조와 데이터 구조를 갖고 어떤 방식으로 기록 확인과 기록 입력을 연결해야 하는지 정의한다.

## Design Position

v1의 중심 가치는 `빠른 입력`이 아니라 `기록 확인과 누적 관리`다.

사용자는 여러 출처에 흩어진 자신의 기록을 이 앱에 직접 입력하고,
앱은 이를 시즌/통산 기준으로 누적 계산해 보여준다.
이때 경기 입력은 제품의 얼굴이 아니라 기록 관리 가치를 유지시키는 핵심 행동으로 둔다.

즉 설계 우선순위는 아래와 같다.

1. 기록이 한곳에 계속 쌓이고 관리된다는 감각
2. 이번 시즌 핵심 지표를 명확히 보는 경험
3. 경기 후 기록을 실제로 계속 추가할 수 있는 입력 흐름

## Product Boundaries

### Product Identity

v1은 아래 제품으로 정의한다.

- 개인 선수 전용
- 모바일 웹 우선
- 기록 확인 중심
- 경기 입력 보조 강화

### User Boundary

- 계정 1개는 선수 프로필 1개와 연결된다.
- 사용자는 자신의 기록만 관리한다.
- 다른 선수 기록을 대신 관리하지 않는다.
- 하나의 실제 경기를 여러 사용자가 공유하는 협업 모델은 v1에 넣지 않는다.

### Scope Boundary

v1은 팀 운영 도구가 아니다.
또한 리그 관리 도구도 아니다.

따라서 아래 항목은 설계 대상에서 제외한다.

- 팀 로스터 관리
- 팀 공동 입력
- 다중 선수 프로필 관리
- 타인 기록 대리 관리
- 외부 기록 자동 연동
- 최근 경기 전용 화면
- 상세 로그 입력

## Mobile Web Design Principles

### Principle 1: Record View First

기본 홈은 `기록 확인 요약 화면`이다.
기록이 하나도 없어도 홈은 바뀌지 않는다.

즉 v1의 첫 화면은 아래 역할을 동시에 가져야 한다.

- 이번 시즌 기록 구조를 보여준다.
- 기록이 쌓일 자리라는 감각을 준다.
- 다음 행동으로 `경기 추가`를 유도한다.

### Principle 2: Input Must Stay Practical

모바일이라는 이유로 핵심 입력 항목을 줄이지 않는다.
타자와 투수의 기본 기록 항목은 모두 입력 가능해야 한다.

대신 모바일 사용성은 아래 방식으로 확보한다.

- 단계 분리
- 필드 그룹화
- 숫자 입력 방식 최적화
- 저장 전 검증
- 이탈 시 경고
- 단계/탭 전환 시 값 유지

### Principle 3: Clarity Beats Speed

판단이 갈릴 때는 입력 속도보다 기록 관리의 명확성을 우선한다.

즉 첫 화면의 정보 밀도는 입력 유도를 위해 제품 정체성을 해치지 않는 수준으로 설계하고,
입력 화면은 짧아 보이게 만드는 것보다 `실수 없이 다시 볼 수 있는 기록을 남기는 것`을 우선한다.

### Principle 4: Mobile Constraints Are Real

문서는 아래 상황을 기본 전제로 가진다.

- 스마트폰 세로 화면
- 한 손 사용 가능성
- 짧은 집중 시간
- 경기 직후 입력
- 나중에 다시 정리 입력
- 저장 실패 가능성
- 입력 중 이탈 가능성

## Core User Flow

1. 사용자가 구글 로그인으로 인증을 완료한다.
2. 기본 홈인 기록 확인 요약 화면으로 진입한다.
3. 사용자는 이번 시즌 핵심 지표를 먼저 본다.
4. 더 많은 지표가 필요하면 `기록 보기`를 통해 상세 기록 화면으로 이동한다.
5. 새 경기 기록이 생기면 `경기 추가`를 통해 경기 입력 화면으로 이동한다.
6. 경기 정보를 입력한다.
7. 타자 기록과 투수 기록 중 필요한 항목을 입력한다.
8. 저장 후 다시 기록 확인 요약 화면으로 돌아온다.
9. 누적 반영된 이번 시즌 기록을 확인한다.

## Scenario Coverage

같은 정보구조는 아래 3가지 대표 시나리오를 모두 지원해야 한다.

- 시즌 중간 점검
  - 기록 확인 요약 화면을 바로 열어 현재 시즌 성적을 확인한다.
  - 필요하면 상세 기록 화면으로 들어가 더 깊게 본다.
- 경기 직후 입력
  - 기록 확인 요약 화면에서 `경기 추가`로 이동해 새 경기를 남긴다.
- 시즌 마감 정리
  - 여러 날에 걸쳐 누락된 경기를 추가하며 시즌 기록을 완성한다.

즉 정보구조는 한 번의 즉시 입력만 지원하는 구조가 아니라,
`확인`, `추가`, `누적`, `정리`가 모두 같은 기록 화면 중심 흐름 안에서 이어져야 한다.

## Information Architecture

### Primary Structure

v1은 전역 탭바 중심 구조보다 `기록 화면 중심 단일 흐름`을 우선한다.

프론트엔드 구현 기술은 Next.js를 기준으로 하되,
이 문서의 정보구조와 화면 책임은 특정 프레임워크의 파일 구조보다 우선한다.

핵심 구조는 아래와 같다.

- 인증 화면
- 기록 확인 요약 화면
- 상세 기록 화면
- 경기 생성 및 기록 입력 화면

즉 사용 흐름은 사실상 아래 순환에 가깝다.

`요약 보기 -> 필요 시 상세 기록 -> 경기 추가 -> 입력 -> 다시 요약 보기`

### Detail Screen Axes

상세 기록 화면은 아래 축으로 구성한다.

이 화면은 저장된 개별 경기 상세 화면이 아니라,
시즌/통산 누적 기록을 더 많이 보여주는 상세 화면이다.

- 시간 축: `이번 시즌 / 통산 / 특정 시즌`
- 기록 축: `타자 / 투수`
- 경기 필터: `전체 / 리그 / 비공식 경기`

### Default Entry

- 기본 진입은 `이번 시즌`
- 기본 기록 축은 사용자 선택값을 유지할 수 있으나, 초기 진입 기준은 문서에서 한쪽으로 강제하지 않는다
- 경기 필터 기본값은 `전체`

## Frontend Delivery Note

프론트엔드는 Next.js App Router 기준으로 구현한다.
다만 v1의 주 화면은 로그인 후 개인 기록 관리 영역이므로,
SSR은 향후 공개 페이지 확장 가능성을 위한 기반으로 이해하고 현재 설계 판단은 모바일 사용성과 정보구조를 우선한다.

## Authentication Design

v1 인증은 `구글 로그인 + 앱 내부 access token / refresh token 기반 세션`으로 설계한다.

### Included

- 구글 로그인
- 로그아웃
- 토큰 재발급

### Ownership Rule

모든 경기와 기록 데이터는 로그인한 사용자 개인 소유로 분리 관리한다.
즉 데이터 조회와 저장은 항상 현재 로그인한 사용자 기준으로 동작한다.

### Logout Rule

로그아웃은 단순 클라이언트 토큰 제거가 아니라 refresh token 무효화를 포함한다.
위치는 기록 확인 요약 화면 상단의 프로필 메뉴를 기본으로 한다.

### Google Login Direction

- 사용자는 구글 계정으로 로그인한다.
- 구글 인증 성공 후 앱은 자체 세션을 위한 토큰을 발급한다.
- v1은 이메일/비밀번호 회원가입과 로그인을 지원하지 않는다.
- Google 계정 1개는 앱 계정 1개와 연결된다.
- 서로 다른 Google 계정은 서로 다른 앱 계정으로 취급한다.
- v1은 계정 연결과 계정 병합을 지원하지 않는다.

## Data Model

### Account And Player Identity

v1에서는 `계정 = 선수 프로필` 관계를 사용한다.

즉 별도의 다중 프로필 계층을 도입하지 않고,
한 사용자가 자신의 기록을 직접 관리하는 구조로 간다.

또한 인증 수단은 Google 로그인 하나로 제한한다.
사용자가 다른 Google 계정으로 로그인하면 다른 앱 계정으로 간주한다.

### Game

`Game`은 사용자의 개인 경기 기록 단위다.
공유 경기 엔티티가 아니라, 사용자가 자신의 누적 기록 관리를 위해 소유하는 기록 객체로 본다.

#### Fields

- 날짜
- 시즌/연도
  - 기본은 경기 날짜 기준 자동 설정
  - 필요 시 사용자가 수정 가능
- 경기 유형
  - `LEAGUE`
  - `NON_OFFICIAL`
- 소속 팀
- 상대 팀
- 메모

### Batter Record

한 경기 안에서 선택적으로 입력 가능하다.

#### Basic Input

- 타석
- 타수
- 1루타
- 2루타
- 3루타
- 홈런
- 볼넷
- 삼진
- 사구

#### Additional Input

- 타점
- 득점
- 도루
- 도루자
- 희생타

#### Calculated Values

- 총안타
- 타율
- 출루율
- 장타율
- OPS

#### Rule

`안타`는 직접 입력받지 않고,
총안타는 `1루타 + 2루타 + 3루타 + 홈런`으로 계산한다.

### Pitcher Record

한 경기 안에서 선택적으로 입력 가능하다.

#### Basic Input

- 이닝
- 추가 아웃 수 (`0`, `1`, `2`)
- 실점
- 자책
- 피안타
- 볼넷
- 삼진

#### Additional Input

- 사구
- 피홈런
- 상대한 타자 수
- 승
- 패
- 세이브
- 홀드

#### Calculated Values

- ERA
- WHIP
- 피안타율
- 탈삼진율

#### Rule

사용자는 `이닝 + 추가 아웃 수`로 입력하고,
내부 저장은 `outsRecorded` 정수로 변환한다.

예:

- `4이닝 0아웃 -> 12`
- `3이닝 2아웃 -> 11`

## Input Design

### Input Unit

v1의 입력 단위는 `경기 단위 요약 입력`이다.
타석별 로그, 이닝별 로그, pitch-by-pitch 입력은 제외한다.

### Input Flow

입력 흐름은 아래 두 단계로 본다.

1. 경기 정보 입력
2. 기록 입력

기록 입력 단계 안에서는 타자 기록과 투수 기록을 필요한 만큼 입력한다.

### Input State Rules

- 타자만 입력 가능
- 투수만 입력 가능
- 둘 다 입력 가능
- 단계 전환 시 값 유지
- 타자/투수 탭 전환 시 값 유지
- 화면 이탈 시 경고
- 완전한 로컬 드래프트 복구는 v1 필수 범위로 두지 않음

### Validation Direction

한 필드라도 입력한 기록 세트는 유효성 검증 대상이 된다.
즉 완전히 비어 있으면 미입력으로 간주하고,
일부라도 입력했다면 유효한 기록 세트인지 검사한다.

## Integrated Record Design

### Home Behavior

기록 확인 요약 화면은 v1의 기본 홈이다.

데이터가 없어도 아래 구조를 유지한다.

- 화면 제목
- 이번 시즌 기준 컨텍스트
- 핵심 지표 요약
- 경기 추가 행동
- 상세 기록 화면 진입 행동

### Empty State

빈 상태는 설명 화면으로 대체하지 않는다.
0 지표 기반 기록 구조를 먼저 보여주고,
그 아래에서 기록이 없다는 안내와 `경기 추가` 행동을 제공한다.

### First-screen Priority

첫 화면의 우선순위는 아래와 같다.

1. 이번 시즌 핵심 지표 요약
2. 경기 추가 행동
3. 상세 기록 화면 진입 행동
4. 현재 기준 정보

### Batter View

#### Summary Metrics

- 경기수
- 타수
- 총안타
- 타율
- OPS

#### Detailed Metrics

- 1루타
- 2루타
- 3루타
- 볼넷
- 사구
- 도루
- 도루자
- 희생타
- 득점

### Pitcher View

#### Summary Metrics

- 경기수
- 이닝
- 승
- ERA
- WHIP
- 삼진

#### Detailed Metrics

- 자책
- 실점
- 피안타
- 피홈런
- 볼넷
- 사구
- 상대한 타자 수
- 피안타율
- 탈삼진율

## Stats Display Rules

- 요약 지표와 상세 지표를 구분한다.
- 모바일 첫 화면은 요약 지표를 우선한다.
- 상세 지표는 별도 상세 기록 화면에서 충분히 확인할 수 있어야 한다.
- 기록이 없어도 수치 구조는 유지한다.
- 타자 요약/대표 지표는 `경기수, 타수, 총안타, 타율, OPS`로 고정한다.
- 투수 요약/대표 지표는 `경기수, 이닝, ERA, WHIP, 삼진, 승`으로 고정한다.
- 타율과 OPS는 소수 셋째 자리까지 표시한다.
- ERA와 WHIP는 소수 둘째 자리까지 표시한다.
- 0분모 비율 지표는 v1에서 `0.000` 또는 `0.00`으로 표기한다.
- 투수 표시는 `0.0 / 0.1 / 0.2` 형식을 사용한다.

## Non-happy-path States

문서와 구현은 정상 흐름만 다루지 않는다.
아래 상태를 반드시 설계 대상에 포함한다.

- 빈 기록 상태
- 구글 로그인 실패 상태
- 구글 로그인 취소 상태
- 인증 만료 상태
- 저장 중 상태
- 저장 실패 상태
- 입력 중 이탈 시 확인 상태

## Backend Architecture Direction

백엔드는 `Spring Boot + Java` 기반으로 설계한다.

최상위 기준은 기능보다 레이어를 우선하며,
각 레이어 안에서 `auth`, `game`, `stats` 도메인을 나눈다.

예상 레이어는 아래와 같다.

- `domain`
  - 엔티티, 값 객체, 핵심 규칙
- `application`
  - 유스케이스 조합, 서비스 흐름
- `infrastructure`
  - JPA, 보안, 설정, 외부 구현
- `presentation`
  - Controller, Request/Response DTO

즉 패키지 방향은 아래 구조를 기본으로 한다.

- `domain.auth`
- `domain.game`
- `domain.stats`
- `application.auth`
- `application.game`
- `application.stats`
- `infrastructure.security`
- `presentation.auth`
- `presentation.game`
- `presentation.stats`

## Backend Support Requirements

백엔드는 아래를 지원해야 한다.

- 사용자 개인 소유 데이터 저장
- 경기 생성
- 타자 기록 저장
- 투수 기록 저장
- 시즌 기준 통합 기록 조회
- 통산 기준 통합 기록 조회
- 경기 유형 기준 필터 조회

아래는 v1 설계 범위에서 제외한다.

- 최근 경기 전용 API
- 팀/공동 입력 모델
- 외부 기록 연동 API

## V1 Scope

### Included

- 구글 로그인
- 로그아웃
- access token / refresh token 기반 인증
- 경기 생성
- 타자/투수 경기 요약 기록 입력
- 한 경기에서 타자/투수 기록 동시 입력
- 시즌/통산 자동 누적 계산
- 기록 확인 요약 화면
- 타자/투수 전환
- 경기 유형 필터
- 날짜 기반 시즌 자동 설정 및 수동 수정
- 빈 기록 화면 제공
- 모바일 웹 기준 입력 상태와 비정상 상태 처리

### Excluded

- 팀 생성
- 선수 등록을 통한 로스터 운영
- 다중 선수 프로필 관리
- 타인 기록 대리 관리
- 게임원/외부 사이트 자동 연동
- 경기 수정/삭제
- 타석별 상세 로그 입력
- 이닝별 상세 로그 입력
- 최근 경기 전용 화면
- 커뮤니티 기능
- 리그 운영 기능
- 영상 업로드/편집 기능
- 완전한 로컬 드래프트 복구

## Key Decisions

- v1의 핵심 가치는 `통합 기록 조회와 누적 관리`다.
- 기본 홈은 `기록 확인 요약 화면`이다.
- 입력은 수동 입력만 지원한다.
- 입력은 필수 행동이지만 제품의 얼굴은 기록 확인이다.
- 기록과 경기 데이터는 사용자별로 분리 관리한다.
- 계정 1개는 선수 프로필 1개와 연결된다.
- 빈 상태에서도 기록 화면 구조를 유지한다.
- 경기 유형과 시즌 구분은 조회를 위한 핵심 메타데이터다.
- 경기 직후 입력과 나중 정리 입력을 모두 고려한다.
- 모바일 사용성은 입력 항목 축소보다 상태/단계 설계로 해결한다.
- 백엔드는 Spring Boot + Java 기준으로 간다.
