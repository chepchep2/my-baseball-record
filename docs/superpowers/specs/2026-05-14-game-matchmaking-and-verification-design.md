# Game Matchmaking And Verification Design

## 목적

현재 MBR은 사용자가 바로 날짜와 시간을 넣고 자기 기록 1건을 저장하는 흐름이다.

이번 변경의 목적은 다음과 같다.

- 기록 입력 전에 먼저 `같은 경기`를 찾거나 만들 수 있게 한다.
- 여러 사용자가 하나의 공용 경기를 공유하게 한다.
- 같은 경기 안에서 각 사용자가 자기 타자 기록 1개를 남기게 한다.
- 같은 경기의 기록 참여자 또는 경기 생성자가 다른 사람 기록을 인증할 수 있게 한다.
- 기존 사용자 기록과 홈/통계 화면은 깨지지 않게 유지한다.

## 현재 문제

- 지금 구조에서는 경기라는 개념이 사실상 `내 개인 기록 1건`과 같다.
- 그래서 같은 경기에서 여러 사용자가 함께 기록을 남기더라도 서로 연결되지 않는다.
- 기록 신뢰도를 높일 수 있는 인증 구조도 없다.
- 같은 경기인데도 서로 다른 시간/장소 표기로 흩어질 수 있다.

## 1차 목표

- 경기 생성/탐색/선택 흐름을 추가한다.
- 새 경기와 기존 경기 모두 경기 상세 화면을 먼저 보게 한다.
- 경기 상세 화면에서 현재 경기의 기록 목록을 본다.
- 사용자는 거기서 `내 기록 입력하기`로 들어간다.
- 기록을 남긴 사용자만 그 경기의 참여자로 본다.
- 같은 경기에서 기록을 남긴 사용자 또는 경기 생성자는 다른 사람 기록을 인증할 수 있다.
- 1명이라도 인증하면 그 기록은 `인증 기록`으로 표시한다.

## 제외 범위

- 투수 기록 연결
- 인증 인원 수 노출
- 인증 등급/가중치
- 경기 참여 승인
- 일정 알림
- 운영자 수동 정리 도구

## 사용자 흐름

### 1. 경기 생성 시작

- 사용자는 `+`로 진입한다.
- 첫 화면 제목은 `경기 생성`이다.
- 날짜는 기존 인라인 달력 UI를 그대로 사용한다.
- 시간은 기존 시/분 선택 UI를 그대로 사용한다.
- 지역은 `시/도`, `구/군` 2단계 선택으로 입력한다.
- `김해시`처럼 일반적인 `구/군` 구조가 아닌 경우에도 두 번째 선택값에는 그냥 `김해시` 자체를 보여준다.

### 2. 기존 경기 후보 조회

- 사용자가 날짜, 시간, 지역을 정하고 `다음`을 누른다.
- 시스템은 같은 날짜 기준으로 기존 경기 후보를 보여준다.
- 탐색 시간 범위는 입력 시각 기준 `±30분`이다.
- 기본 탐색 범위는 같은 `구/군`이다.
- `더 보기`를 누르면 더 넓은 범위로 탐색할 수 있다.
- 후보 카드에는 다음 정보만 보여준다.
  - 날짜
  - 시간
  - 지역
  - 구장명

### 3. 기존 경기 선택

- 사용자가 기존 경기 후보를 누르면 바로 기록 입력으로 가지 않는다.
- 먼저 해당 경기의 경기 정보 화면으로 이동한다.
- 경기 정보 화면에서 현재 기록이 남아 있는 사용자 목록을 본다.
- 사용자는 그 화면에서 `내 기록 입력하기`로 들어간다.

### 4. 새 경기 생성

- 기존 경기 후보가 없거나 사용자가 직접 새 경기를 만들고 싶으면 `새 경기`로 간다.
- 해당 지역에서 이미 등록된 구장 추천 목록을 먼저 보여준다.
- 사용자는 추천 목록에서 선택하거나 직접 입력할 수 있다.
- 직접 입력 시 기존 구장과 유사한 이름이 있으면 다음 둘 중 하나를 명시적으로 고르게 한다.
  - 기존 구장 선택
  - 새 구장 추가

### 5. 경기 정보 화면

- 경기 생성 또는 기존 경기 선택 후에는 먼저 경기 정보 화면으로 이동한다.
- 경기 정보 화면은 경기 단위 허브 역할을 한다.
- 최소 표시 정보는 다음과 같다.
  - 날짜
  - 시간
  - 지역
  - 구장명
- 그 아래에 현재 기록 카드 리스트를 세로로 보여준다.
- 현재 사용자가 아직 기록이 없으면 `내 기록 입력하기`를 보여준다.
- 현재 사용자가 이미 기록이 있으면 `내 기록 상세/수정` 흐름으로 확장할 수 있다.
- 생성자나 기록 참여자가 아니어도 경기 정보 화면과 다른 사람 기록은 볼 수 있다.
- 다만 인증은 할 수 없다.
- 기본은 5개만 먼저 보여주고 `더 보기`로 나머지 기록을 펼친다.

### 6. 전체 경기 목록

- 홈의 `더보기` 목적지는 `/games`가 아니라 `/matches`다.
- `/matches`에서는 내가 기록을 남긴 경기들을 최신순으로 본다.
- 연도/월 필터를 제공한다.
- 카드 클릭 시 경기 정보가 아니라 각 경기의 `내 기록 상세`로 이동한다.
- 카드에는 `인증됨 / 인증 전` 배지를 함께 보여준다.

### 7. 경기 기록 상세

- 기록 상세는 기존 배포 환경의 경기 기록 상세 구조를 따르되 읽기 전용으로 본다.
- 최소 표시 정보는 다음과 같다.
  - 날짜
  - 시간
  - 타율
  - 출루율
  - 장타율
  - OPS
  - 타석
  - 사사구
  - 1루타
  - 2루타
  - 3루타
  - 홈런
- 상세 하단에는 `경기 정보로`를 둔다.
- 본인 기록일 때만 `수정`, `삭제`를 둔다.
- 다른 사람 기록은 읽기 전용이다.

### 8. 참여자 판단

- 1차에서는 별도 참여자 테이블을 두지 않는다.
- `기록 입력을 완료한 사용자`만 그 경기의 참여자로 본다.
- 즉 경기 생성만 하고 기록을 남기지 않은 상태는 최종 참여자로 보지 않는다.

### 9. 인증

- 인증 가능자는 다음 두 경우다.
  - 같은 경기에서 기록을 남긴 사용자
  - 그 경기를 만든 생성자
- 같은 사람이 같은 기록을 두 번 인증할 수는 없다.
- 여러 명이 같은 기록을 각각 인증하는 것은 가능하다.
- 화면에는 인증 수를 보여주지 않는다.
- 1명이라도 인증이 있으면 `인증 기록`으로 표시한다.
- 이미 인증된 기록을 수정하면 기존 인증은 자동 해제되고 다시 `인증 전`이 된다.

## 장소/구장 처리

### 명칭

- 1차에서는 `location`보다 `stadium` 용어를 사용한다.
- 이유는 실제 사용자 문맥이 `삼락A`, `맥도B`, `BPA 야구장`처럼 구장 단위이기 때문이다.

### 추천과 직접 입력

- 지역을 고르면 해당 지역의 기존 `stadium` 추천 목록을 보여준다.
- 사용자가 새 이름을 직접 넣을 수 있다.
- 다만 중복을 줄이기 위해 유사 이름이 있으면 명시적으로 선택하게 유도한다.

### 유사 이름 기준

- 완전 일치만 보지 않는다.
- 띄어쓰기, 대소문자, 일부 표현 차이까지 흡수한다.
- 예:
  - `삼락A`
  - `삼락 A`
  - `삼락구장A`
  - `삼락 생태공원 A`

## 데이터 구조 방향

### 핵심 개념

- `game_record`는 앞으로 `공용 경기`로 사용한다.
- `batter_record`는 그 경기 안에서 사용자별 타자 기록으로 사용한다.
- 즉 관계는 다음과 같다.

- `game_record` 1개
  - 조상우 `batter_record`
  - 김영훈 `batter_record`
  - 서세홍 `batter_record`

이 방향이 필요한 이유는 공용 경기와 개인 기록을 자연스럽게 분리하기 위해서다.

### 기존 데이터 보존 원칙

- 기존 `game_record`, `batter_record` 데이터는 유지한다.
- 기존 사용자 기록은 홈/통계에서 계속 보여야 한다.
- 새 구조는 점진적으로 적용한다.
- 즉 기존 데이터는 깨지지 않아야 한다.

## 1차 테이블 방향

### 1. `game_record`

공용 경기 상위 엔티티로 사용한다.

기존 필드에 더해 아래 성격을 가진다.

- 경기 날짜/시간
- 생성자
- 지역
- 구장

추가 후보 필드:

- `created_by_user_id`
- `city_name`
- `district_name`
- `stadium_id`
- `stadium_name_snapshot`
- `record_scope` 또는 유사 플래그

설명:

- 기존 데이터와 새 데이터를 함께 다루기 위해 구분 정보가 필요할 수 있다.
- 새 구조에서는 `user_id`를 더 이상 기록 주인으로만 보지 않고, 생성자 의미와 legacy 의미를 함께 고려해야 한다.

### 2. `batter_record`

사용자별 타자 기록 엔티티로 확장한다.

추가/변경 후보:

- `user_id` 추가
- 기존 `game_id UNIQUE` 제거
- 대신 `(game_id, user_id)` unique 추가

설명:

- 한 경기 아래에 여러 사람의 기록이 달려야 하므로 `game_id` 단독 unique는 제거해야 한다.
- 한 사람은 한 경기에서 타자 기록 1개만 가지므로 `(game_id, user_id)`는 unique여야 한다.
- 기존 데이터는 `batter_record.user_id = 기존 game_record.user_id`로 백필한다.

### 3. `stadium`

구장 추천/중복 방지용 테이블

필드 후보:

- `id`
- `city_name`
- `district_name`
- `stadium_name`
- `normalized_name`
- `created_by_user_id`
- `created_at`
- `updated_at`

### 4. `game_record_verification`

기록 인증용 테이블

필드 후보:

- `id`
- `batter_record_id` 또는 `game_record_id`
- `verified_by_user_id`
- `created_at`

1차 권장:

- 인증 대상은 실제 사용자별 타자 기록이므로 `batter_record_id`를 직접 거는 쪽이 더 자연스럽다.
- 같은 사람이 같은 기록을 두 번 인증하지 못하게 복합 unique 제약을 둔다.

예:

- unique `(batter_record_id, verified_by_user_id)`

## 읽기 호환성

- 홈/통계는 기존 데이터와 새 데이터를 함께 읽을 수 있어야 한다.
- 기존 데이터는 지금처럼 보여야 한다.
- 새 구조에서는 결국 사용자별 통계 집계 기준이 `batter_record.user_id` 중심으로 이동하는 쪽이 안전하다.
- 이 전환은 스키마 변경 후 읽기 로직을 단계적으로 옮긴다.

## 설계 결론

1차는 다음 기준으로 진행한다.

- 경기 입력 전에 먼저 경기 후보를 찾거나 만든다.
- 기존 경기와 새 경기 모두 경기 정보 화면으로 먼저 들어간다.
- 기록을 남긴 사람만 참여자로 본다.
- 생성자 또는 기록 참여자는 인증할 수 있다.
- 1명이라도 인증이 있으면 인증 기록이다.
- 기존 데이터는 절대 깨지지 않아야 한다.
- 새 구조는 `game_record = 공용 경기`, `batter_record = 사용자별 타자 기록` 방향으로 확장한다.
