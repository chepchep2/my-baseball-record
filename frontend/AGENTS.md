# Frontend AGENTS

## Purpose

이 폴더의 프론트엔드는 `모바일 웹 사용성`을 최우선으로 둔다.
화면을 많이 만드는 것보다, 사용자가 실제로 `기록을 남기고, 찾고, 고치고, 삭제할 수 있는가`를 더 중요하게 본다.

이 프로젝트의 프론트엔드는 특히 아래를 기준으로 작업한다.

- 게임원을 대신해서 써볼 만한 사용성인가
- 한 손 조작과 빠른 복귀가 가능한가
- happy path뿐 아니라 이탈, 복구, 실패, 수정 흐름까지 설계되었는가
- 문서에 정의된 정보구조와 화면 역할을 임의로 흐리지 않는가

## Product Principles

- 기본 구조는 하단 탭 `홈 / 기록 / 생성 / 경기 / 내 정보`를 유지한다.
- `홈`은 현재 시즌 핵심 요약만 담당한다.
- `기록`은 누적 기록 상세만 담당한다.
- `경기`는 캘린더 기반 경기 관리와 개별 경기 진입을 담당한다.
- `개별 경기 상세`는 읽기 전용 확인 화면이며 수정/삭제의 진입점이다.
- `생성`과 `수정`은 같은 입력 화면 구조를 공유한다.

## Architecture Principles

- 페이지는 조합과 라우팅에 집중하고, 복잡한 UI/상태 로직은 하위 컴포넌트나 훅으로 분리한다.
- 공용 UI와 도메인 UI를 구분한다.
- 서버 상태와 로컬 UI 상태를 분리한다.
- 입력 draft, 탭 전환, 복구 모달 같은 로컬 흐름은 프론트에서 책임진다.
- API 응답 shape는 문서 계약과 다르게 임의 해석하지 않는다.

## Folder Responsibilities

- `src/app`
  - 라우트와 페이지 진입점
  - 레이아웃, 전역 스타일, 페이지 수준 composition
- `src/components`
  - 재사용 가능한 UI
  - 하단 탭, 캘린더, 모달, 카드, 입력 섹션
- `src/features`
  - 도메인별 화면 조각, 훅, 상태, 변환 로직

## UX Rules

- 모바일에서 탭 이동과 복귀가 항상 명확해야 한다.
- 작은 화면에서 헤더와 필터가 과밀해지지 않게 한다.
- 입력 화면은 긴 단일 폼보다 `구성 단위`로 분리한다.
- 생성/수정 중에는 이탈 시나리오를 반드시 고려한다.
- 빈 상태, 로딩 상태, 실패 상태, 복구 상태를 정상 흐름과 같은 중요도로 다룬다.
- 수정/삭제처럼 위험한 행동은 안전한 확인 단계를 거친다.

## Draft And Recovery Rules

- 생성/수정 모두 localStorage draft를 사용한다.
- 입력값 변경 시 자동 저장한다.
- 같은 세션 안 복귀는 자동 복구한다.
- 브라우저 재진입 시에는 복구 확인 모달을 띄운다.
- 최종 저장 성공 시 draft를 삭제한다.
- draft 정책은 문서 계약을 우선하며, 임의로 서버 부분 저장으로 바꾸지 않는다.

## State Rules

- 홈/기록의 누적 조회 상태와 생성/수정의 draft 상태를 섞지 않는다.
- 캘린더 선택 상태와 경기 목록 상태를 분리한다.
- 개별 경기 상세는 읽기 전용 상태를 유지하고, 수정은 별도 모드로 전환한다.
- optimistic update는 문서에 없는 한 함부로 도입하지 않는다.

## Refactoring Rules

- 리팩토링은 화면을 더 예쁘게 만드는 것보다 구조를 더 명확하게 만드는 방향이어야 한다.
- 페이지 파일이 비대해지면 섹션 단위 컴포넌트로 분리한다.
- 도메인 규칙이 여러 화면에 반복되면 공통 훅이나 유틸로 이동한다.
- 문서에 정의되지 않은 새로운 정보구조나 액션을 임의 추가하지 않는다.
- 리팩토링 후에는 주요 사용자 흐름이 유지되는지 다시 확인한다.

## Testing Rules

- 최소한 아래 흐름은 반복 검증한다.
  - 로그인 진입
  - 하단 탭 이동
  - 홈 요약 조회
  - 기록 화면 필터 전환
  - 경기 생성
  - 수정 모드 진입
  - 삭제 확인 모달
  - draft 저장과 복구
- 버그 수정과 리팩토링은 재현 가능한 시나리오 기준으로 검증한다.
- 모바일 뷰 기준 검증을 우선한다.

## Delivery Rules

- 프론트 작업은 장기적으로 누적될 수 있으므로, 한 번에 큰 변경보다 화면 흐름 단위로 나눈다.
- 배포 링크에서 바로 시연 가능한 상태를 자주 만든다.
- 기능 구현보다 사용성 검증이 먼저일 때는 프로토타입이라도 빠르게 연결한다.
- 문서가 바뀌면 화면 구조도 같이 점검한다.
